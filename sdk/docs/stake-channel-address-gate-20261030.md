# 质押与通道地址双向互斥：实现边界（2026-10-30）

用户已确定同一**具体通道地址**不能同时用于质押和开通道，两个方向都要拒绝；其他地址可正常使用。旧通道恢复、关闭、解押不应因曾经使用过该地址而永久受阻。本页是定点代码事实与待决的持久占位取舍；互斥生产代码和原 `TestCoreNode` case 尚未修改。

现有请求顺序允许在 L1 资金动作之前作服务端准入：SDK `OpenChannel` 在 `wallet/channel_operations.go:27-61` 取得目标地址，`StakeToBeMinner` 在 `wallet/action_remote.go:410-441` 得到目标地址；远程 action 请求在 `wallet/action_remote.go:23-103` 的费用交易广播之前发给服务端。服务端开通道的精确地址从请求 funding key 推导（`transcend/stp/funding.go:125-141`）；质押 action 由 `transcend/stp/action_remote.go:714-737` 接收。现有 `HasStaked` 是按公钥返回布尔值，且底层部分查询吞掉网络错误，不能直接当作精确地址、失败关闭的互斥证明。

仅在两入口各查一次当前状态，改动最少，但两个同时到达的请求都可读到“空”，随后各自提交；因此不满足已确定的并发要求。仅用进程内锁和 reservation 也有重启窗口：开通道的早期 reservation 到 `funding.go:283-319` 才进入内存，完成后才持久化；质押 reservation 在 `action_remote.go:63-118` 先进入内存、费用交易广播后才持久化；`stp/db.go:455-463` 重启时丢弃 `RS_INIT`。服务端接受后到持久化前若重启，早期占位会消失，客户端可能已经继续 L1 资金动作。

满足并发与重启边界的最小候选是复用现有 reservation 生命周期，在**发送准入成功响应之前**按网络、精确地址、用途作原子检查和持久占位；两个业务入口共用该短临界区，网络请求留在锁外。重启时恢复未决占位，未知广播结果不能直接释放，只有经已存在的链状态／交易记录确认终态才清理。维护成本是早期失败和超时占位需要可验证的收尾规则，且须核对服务端是否存在并行实例共享同一权威状态。此候选改变了持久化边界；按根目录 `AGENTS.md` 的复杂性决策规则，先由用户确定，再改生产代码。

不需要为“质押请求先于 L1 广播”另建准备 RPC；但现有查询必须能返回“未质押／已质押／不可确定”三种结果，不得把网络错误当作无质押。原 `TestCoreNode` 同址成功预期已获准改为明确拒绝，并保留另一个非质押地址成功路径；在上述占位决策前不以只改测试或客户端预检声称互斥完成。
